서버와 배포

🛰️

서버는 꼭 커다란 전용 컴퓨터를 뜻하지 않아요.
네트워크 요청을 받아 서비스를 제공하는 역할을 하는 프로그램이나 컴퓨터를 서버라고 불러요. 노트북도 서버 프로그램을 실행하면 잠시 서버 역할을 할 수 있습니다.

사건 파일 · 배포 첫날

“내 컴퓨터에서는 되는데요?”

민지가 웹 프로그램을 완성했어요. 자기 노트북에서는 열리지만 친구의 휴대폰에서는 접속이 안 됩니다. 코드는 멀쩡한데 무엇을 확인해야 할까요?

추리 질문 프로그램을 실행할 컴퓨터, 외부에서 찾아올 주소, 통과를 허용할 네트워크 문이 모두 준비됐을까요?

단서와 풀이 보기

배포는 파일 복사만으로 끝나지 않아요. 서버에서 프로그램이 실행 중인지, 외부에 공개할 포트를 열었는지, 도메인과 DNS가 서버를 가리키는지, 방화벽과 프록시가 요청을 전달하는지 확인해야 합니다. 이 페이지에서 한 단계씩 그 길을 따라가 봅니다.

01

서버와 클라이언트: 부탁하는 쪽과 처리하는 쪽

클라이언트 는 서비스를 요청하는 쪽이고, 서버 는 요청을 받아 응답하는 쪽이에요. 브라우저가 웹 페이지를 요청하면 웹 서버가 요청을 받고, 프로그램의 도움을 받아 페이지나 데이터를 돌려줍니다.

서버는 역할 이름이라 한 서비스가 여러 서버를 사용할 수 있어요. 웹 요청을 받는 웹 서버, 데이터를 저장하는 데이터베이스 서버처럼 각자 맡은 일이 다릅니다.

브라우저와 서버가 주고받는 요청

브라우저요청을 보냄 요청 → 서버요청을 처리 ← 응답 브라우저결과를 표시
이름 하는 일 쉬운 비유
클라이언트 서버에 필요한 작업을 요청 식당에서 주문하는 손님
웹 서버 HTTP 요청을 받고 응답을 전달 주문을 접수하는 직원
애플리케이션 규칙에 따라 계산하고 처리 주방에서 음식을 만드는 요리사
데이터베이스 필요한 정보를 저장하고 조회 재료와 주문 기록을 보관하는 창고

중요 하나의 작은 프로그램이 웹 요청과 데이터 저장까지 전부 할 수도 있어요. 역할을 나누는 방식은 서비스의 크기와 필요에 따라 달라집니다.

02

주소와 웹 통신: 주소를 찾고 서비스 문을 두드려요

도메인 이름은 사람이 읽기 쉬운 주소예요

컴퓨터는 IP 주소를 이용해 네트워크의 목적지를 찾아요. study.example 같은 도메인 이름을 입력하면 DNS가 관련 IP 주소를 찾아 알려줍니다. 전화번호부에서 이름을 검색하는 것과 비슷해요.

HTTP, HTTPS, 포트

브라우저와 웹 서버는 HTTP 규칙에 따라 요청과 응답을 주고받아요. HTTPS는 TLS로 연결을 암호화하고 서버의 신원을 확인할 수 있게 보호하는 HTTP입니다. 포트는 한 컴퓨터 안에서 어느 프로그램으로 통신을 전달할지 구분하는 번호예요.

https :// shop.example : 443 / products/7 보호 방식 · 도메인 · 포트 · 경로
주소 조각 뜻 비유
https 어떤 통신 규칙과 보호 방식을 쓸지 대화 언어와 봉투
shop.example 찾을 서비스의 이름 건물 이름
:443 컴퓨터 안 서비스 통로 번호 건물 안의 창구
/products/7 서버 안에서 요청할 자원 경로 찾을 방과 서류

DNS가 틀린 주소를 알려 주면 서버에 도착하지 못하고, 서버 프로그램이 꺼져 있거나 포트가 막혀도 연결되지 않아요. “웹이 안 된다”는 증상만으로 원인을 단정하지 않는 이유입니다.

03

리눅스와 터미널: 서버에게 글자로 명령하기

많은 서버는 화면과 마우스 대신 터미널에서 명령어로 관리해요. 터미널은 명령을 입력하는 창이고, 셸은 그 명령을 읽어 실행하는 프로그램입니다.

자주 만나는 기본 명령
pwd                 # 현재 폴더가 어디인지
ls -la              # 파일 목록 보기
cd /var/log         # 폴더 이동
mkdir my-app        # 폴더 만들기
cat app.log         # 파일 내용 확인
tail -n 50 app.log  # 마지막 50줄 보기

명령은 현재 위치와 파일 권한의 영향을 받아요. 익숙하지 않은 삭제 명령은 대상과 경로를 확인하기 전 실행하지 말고, 운영 서버에서는 무엇을 바꾸는지 먼저 이해해야 합니다.

파일·사용자·권한

파일 권한은 누가 읽고(r), 수정하고(w), 실행할 수 있는지(x)를 정해요. 프로그램 실행에 필요한 권한만 주는 것이 안전합니다. 관리자 권한은 시스템 전체를 바꿀 수 있으므로 꼭 필요한 경우에만 사용합니다.

개념 뜻 점검 예
경로 파일이 있는 위치 설정 파일 경로가 맞나?
사용자 명령이나 프로그램을 실행하는 계정 서비스가 어떤 계정으로 실행되나?
권한 읽기·쓰기·실행 허용 범위 로그 파일을 읽을 수 있나?
작업 디렉터리 프로세스가 기준으로 삼는 현재 폴더 상대 경로가 어디를 기준으로 하나?
04

프로세스와 설정: 프로그램을 계속 실행하기

실행 중인 프로그램 하나를 프로세스 라고 해요. 서버 프로그램을 터미널에서 실행하면 창을 닫을 때 함께 종료되기도 하므로, 실제 운영에서는 서비스 관리 도구나 컨테이너 등을 이용해 백그라운드 실행과 재시작을 관리합니다.

서버 프로세스는 특정 포트에서 연결을 기다려요. 브라우저가 그 포트로 요청하면 운영체제가 해당 포트를 사용 중인 프로세스에 전달합니다. 이미 다른 프로그램이 사용하고 있으면 포트 충돌이 생겨 실행에 실패할 수 있어요.

Spring 애플리케이션을 포트 8080에서 실행한다고 가정
java -jar app.jar
# 로그에 "Started ..."가 나오는지 확인
# 포트 8080을 다른 프로그램이 사용 중이면 시작 실패 가능

환경 설정과 비밀 값

개발용·검증용·운영용 환경은 데이터베이스 주소나 로그 수준이 다를 수 있어요. 환경 변수나 별도 설정 파일로 값을 분리하면 같은 프로그램을 환경에 맞게 실행할 수 있습니다.

설정 예 보통 공개해도 되는가? 주의할 점
HTTP 포트 번호 대체로 가능 이미 사용 중인 포트인지 확인
데이터베이스 주소 환경에 따라 다름 잘못 연결하면 엉뚱한 DB에 접근
비밀번호·API 비밀 키 아니요 코드 저장소나 화면에 넣지 않기
로그 수준 보통 가능 운영에서 민감한 값을 기록하지 않기

비밀 값 관리 암호, 토큰, 개인 키를 Git 저장소에 올리지 마세요. 환경 변수나 안전한 비밀 관리 도구를 쓰고, 값이 노출됐다면 단순 삭제로 끝내지 말고 키를 폐기하고 교체해야 해요.

05

네트워크 경계: 방화벽과 리버스 프록시

서버가 인터넷에 연결되어도 모든 문을 열어야 하는 것은 아니에요. 방화벽은 주소·포트·방향 같은 규칙을 확인해 통신을 허용하거나 막습니다. 클라우드에서는 보안 그룹이나 NSG 같은 네트워크 규칙이 비슷한 역할을 할 수 있어요.

리버스 프록시는 사용자와 애플리케이션 서버 사이에서 요청을 대신 받아 전달하는 서버예요. TLS 종료, 도메인별 경로 전달, 여러 서버로 요청 나누기, 응답 캐시 같은 일을 맡길 수 있습니다.

브라우저HTTPS 요청 → 방화벽허용 규칙 검사 → 리버스 프록시요청을 중계 → 앱 서버실제 처리

어느 층에서 막혔을까요?

구성 요소 주요 질문 잘못되면 보이는 현상
DNS 도메인이 올바른 IP를 가리키나? 찾을 서버 주소가 틀림
방화벽 필요한 방향·포트가 허용됐나? 연결 시간 초과 또는 거부
리버스 프록시 올바른 앱 서버로 넘기나? 502·504 응답, 잘못된 사이트
애플리케이션 요청을 처리할 경로가 있나? 404·500 응답
06

배포하기: 내 컴퓨터의 코드를 서버에서 실행하기

배포 는 프로그램의 새 버전을 사용자가 접근할 수 있는 환경에 올리고 실행하는 과정이에요. “파일 복사”뿐 아니라 빌드, 설정, 실행, 상태 확인을 포함합니다.

코드 작성 Git에 저장
→
빌드 실행 파일 만들기
→
전달 서버에 배치
→
실행 설정으로 시작
→
확인 로그·상태 검사

안전한 배포의 기본 순서

  1. 어떤 버전을 배포할지 확인하고 빌드합니다.
  2. 운영 설정과 비밀 값이 준비됐는지 점검합니다.
  3. 새 프로세스를 시작하거나 기존 버전을 교체합니다.
  4. 헬스 체크와 로그로 정상 실행을 확인합니다.
  5. 문제가 생기면 이전 정상 버전으로 되돌리는 방법을 준비합니다.

작은 서비스는 수동으로 배포할 수 있지만, 사람이 매번 같은 명령을 입력하면 실수하기 쉬워요. CI/CD는 코드 변경을 빌드·검사·배포하는 반복 작업을 자동화하는 방식입니다. 자동화해도 배포 결과를 확인하고 되돌릴 수 있어야 합니다.

07

운영과 장애 대응: 로그로 무슨 일이 있었는지 찾기

서버가 실행 중이라는 사실만으로 서비스가 정상이라고 단정할 수 없어요. 사용자가 실제 기능을 쓸 수 있는지, 데이터베이스에 연결되는지, 응답이 지나치게 느리지 않은지도 확인해야 합니다.

로그 는 프로그램이 남긴 사건 기록이고, 메트릭 은 CPU 사용률·요청 수·응답 시간처럼 숫자로 변하는 상태예요. 둘을 함께 보면 문제의 시점과 범위를 찾기 쉬워집니다.

로그를 읽을 때 보는 것
2026-09-28 10:22:14 ERROR requestId=ab12 path=/orders
Database connection timed out

# 언제? 어떤 요청? 어떤 오류? 재현 가능한가?

증상별로 범위를 좁혀요

증상 먼저 확인 다음 확인
도메인 접속이 안 됨 DNS 조회 결과 서버 주소가 맞는지
연결 시간이 초과됨 서버 실행·방화벽·경로 포트가 열려 있는지
502 또는 504 프록시와 앱 서버 상태 앱이 요청을 제때 응답하는지
500 오류 앱 로그와 요청 식별자 DB·외부 API·코드 예외
갑자기 느려짐 응답 시간·CPU·메모리 DB 쿼리·요청량·최근 배포

조사 순서 사용자가 본 증상과 발생 시각을 기록하고, 최근 변경 사항을 살펴본 뒤, 요청이 지나온 구성 요소를 바깥에서 안쪽으로 확인하세요. 로그에 비밀번호나 개인 정보가 남지 않도록 주의합니다.

08

데이터베이스와 백업: 서비스가 기억해야 할 것

애플리케이션 프로세스는 재시작될 수 있어요. 회원과 주문처럼 계속 보존해야 할 데이터는 보통 데이터베이스에 저장합니다. 애플리케이션은 네트워크로 데이터베이스에 연결해 조회·추가·변경을 요청해요.

운영 데이터베이스는 외부에 무조건 공개하지 않고, 앱 서버 등 필요한 곳에서만 접근하도록 제한합니다. 연결 계정은 필요한 권한만 주고, 접속 비밀 값은 안전하게 관리해야 합니다.

백업은 실제로 복원할 수 있어야 해요

백업 파일이 있다고 복구가 보장되는 것은 아닙니다. 정기적으로 백업하고, 복원 테스트를 해 보고, 장애가 났을 때 얼마나 오래된 데이터까지 복구할지와 서비스 재개 목표를 정해야 합니다.

질문 의미 예시
무엇을 백업할까? 복구에 필요한 데이터 범위 DB, 업로드 파일, 설정

컨테이너 기초: 실행 환경을 함께 포장하기

내 컴퓨터와 서버의 운영 환경이 다르면 같은 프로그램도 다르게 동작할 수 있어요. 컨테이너는 앱과 필요한 실행 환경을 이미지로 묶어, 여러 환경에서 비슷한 방식으로 실행하도록 도와줍니다.

이미지는 실행을 위한 읽기 전용 설계도에 가깝고, 컨테이너는 그 이미지로 실제 실행한 인스턴스예요. 컨테이너를 쓴다고 보안, 데이터 백업, 네트워크 설정이 저절로 해결되는 것은 아니며 각각 따로 관리해야 해요.

용어 비유 역할
이미지 요리법과 재료를 담은 상자 컨테이너 실행의 기반
컨테이너 상자를 열어 실제로 조리 중인 주방 실행 중인 격리된 프로세스
볼륨 컨테이너 밖의 보관함 재시작 뒤에도 필요한 데이터 보존
포트 매핑 건물의 바깥 문과 방 안 문 연결 호스트 포트에서 컨테이너 서비스로 전달

Linux 확인 명령
systemctl status my-app
journalctl -u my-app --since "10 minutes ago"
ss -lntp
curl -i http://127.0.0.1:8080/health

내부 요청만 성공한다면 방화벽, 보안 그룹, 로드 밸런서, 리버스 프록시를 살펴볼 수 있습니다. 오류 시작 시각과 배포 버전, 자원 사용량, 변경 이력을 함께 기록하세요.

대응 순서 우선 롤백이나 우회로 복구하고 안정화 후 로그와 지표를 바탕으로 재발 방지책을 정리합니다.

심화

요청 흐름을 추적하고 서버 병목 찾기

요청은 여러 대기 지점을 지나가요

요청은 DNS, 연결, 프록시, 애플리케이션, 데이터베이스를 거쳐 응답합니다. 각 단계에 시간 제한이 없으면 한 곳의 지연이 스레드와 연결을 점유해 장애가 번질 수 있습니다. 외부 호출 제한 시간은 전체 요청 제한보다 짧게 두고 재시도 횟수도 제한합니다.

로그·메트릭·추적으로 서로 다른 단서를 모아요

로그는 사건의 문맥, 메트릭은 수치 변화, 분산 추적은 서비스 사이의 요청 경로를 보여 줍니다. 요청 ID를 이어 주면 로그를 연결하기 쉽습니다. 평균 지연뿐 아니라 p95·p99 응답 시간, 오류율, 처리량을 함께 보면 느린 일부 요청도 발견할 수 있습니다.

  • 프로세스 상태와 포트 수신 여부를 먼저 확인합니다.
  • 헬스 체크는 프로세스 생존과 의존 서비스 준비를 구분합니다.
  • 종료 때 새 요청을 중지하고 진행 중인 작업을 정리합니다.
