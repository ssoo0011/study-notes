01

테스트 기초: 입력과 기대 결과 비교하기

테스트는 준비(Arrange), 실행(Act), 확인(Assert)의 세 단계로 생각하면 쉬워요. 주어진 상황에서 동작을 호출하고, 결과가 기대와 같은지 확인합니다.

준비 조건과 입력
→
실행 대상 코드 호출
→
확인 기대값 비교

테스트 범위의 균형

종류 확인 범위 장점·비용 예
단위 작은 메서드·클래스 빠르고 원인 찾기 쉬움 할인 계산
통합 여러 컴포넌트 연결 실제 연결 확인, 더 느림 Service + DB
시스템/E2E 사용자 관점의 전체 흐름 현실적이나 느리고 유지 비용 큼 브라우저에서 로그인

모든 것을 가장 큰 테스트로 검사하면 느리고 실패 원인도 찾기 어려워요. 빠른 단위 테스트를 충분히 두고, 중요한 통합과 핵심 사용자 시나리오를 보완합니다.

02

테스트 범위와 테스트 대역

단위 테스트는 외부 DB나 네트워크 없이 핵심 로직을 빠르게 확인하는 데 유용해요. 통합 테스트는 실제 설정과 데이터베이스 등 여러 요소가 연결되는지를 검사합니다.

테스트 대역은 협력 객체를 대신해요

Mock이나 Fake는 외부 시스템을 테스트에서 대체하는 방법이에요. 항상 Mock을 많이 쓰는 것이 좋은 것은 아니며, 구현 세부 호출 횟수에 너무 의존하면 내부 구조 변경에도 테스트가 깨질 수 있습니다.

대역 설명 사용 예
Stub 미리 정한 응답 제공 외부 API 응답 흉내
Mock 호출 여부·전달 값을 검증 알림 발송 요청 확인
Fake 간단한 동작을 실제처럼 구현 메모리 기반 저장소

실제 DB와 대역 중 무엇을 쓸지 테스트 목적을 기준으로 선택하세요. 저장 쿼리와 트랜잭션을 확인하려면 실제 DB를 사용하는 통합 테스트가 필요할 수 있어요.

03

좋은 테스트 입력: 정상값뿐 아니라 경계값 확인

예를 들어 점수가 0~100이어야 한다면 정상값 75뿐 아니라 경계값 0과 100, 그 바깥의 -1과 101도 확인해요. 동치 분할은 같은 방식으로 처리될 것으로 예상되는 입력들을 그룹으로 나누어 대표값을 고르는 기법입니다.

값 검증 조건 테스트 입력 예 기대 결과
1 이상 10 이하 1, 5, 10 허용
하한 미만 0 거절
상한 초과 11 거절
누락 null 또는 빈 값 요구사항에 맞는 오류

테스트 이름에는 조건과 기대 동작을 드러내세요. 실패했을 때 어떤 규칙이 깨졌는지 빨리 이해할 수 있어야 합니다.

04

TDD와 자동 검사: 작은 주기로 만들기

TDD(테스트 주도 개발)는 실패하는 테스트를 먼저 작성하고, 통과할 만큼 코드를 만들고, 구조를 정리하는 반복 방식이에요. 모든 상황에 맞는 의식은 아니지만, 요구사항을 명확히 하고 작은 변경으로 확인할 때 도움이 됩니다.

Red 실패 테스트
→
Green 통과할 최소 코드
→
Refactor 구조 정리
↻

CI에서 자동 검사하기

CI는 코드를 저장소에 올릴 때마다 자동으로 빌드하고 테스트해 변경 문제를 일찍 찾는 방식이에요. 자동화 검사는 반복 가능한 품질 신호이지, 요구사항 검토나 사람의 코드 리뷰를 모두 대신하지는 않습니다.

05

디버깅: 재현하고 범위를 좁히기

오류가 나면 무작정 코드를 여기저기 바꾸지 말고, 입력·환경·발생 시각·오류 메시지를 기록해 문제를 재현해요. 재현 절차가 작을수록 원인을 찾기 쉽습니다.

로그와 디버거 사용

도구 도와주는 일 질문
로그 실행 중 남긴 사건 기록 오류 직전에 어떤 일이 있었나?
브레이크포인트 지정한 줄에서 실행 멈춤 이 시점 변수 값은 무엇인가?
스택 추적 예외가 발생한 호출 경로 표시 어떤 함수들이 여기까지 왔나?
Network 도구 브라우저 요청과 응답 확인 어떤 URL과 상태 코드인가?

문제를 고친 뒤 실패하던 사례를 테스트로 남기면 같은 문제가 다시 나타나는 것을 막는 데 도움이 돼요. 로그에는 비밀번호나 인증 토큰을 기록하지 않습니다.

06

리팩터링: 동작을 유지하면서 구조 개선

리팩터링은 외부에서 보이는 동작을 바꾸지 않고 코드 구조를 더 이해하기 쉽게 바꾸는 작업이에요. 테스트가 있으면 정리 과정에서 기능이 깨졌는지 확인하기 쉽습니다.

신호 개선 방향
한 메서드가 너무 많은 역할 이름이 분명한 작은 메서드로 분리
같은 규칙이 여러 곳에 복사 공통 규칙을 한 곳에서 관리
이름만 보고 목적을 알기 어려움 역할과 결과가 드러나도록 이름 수정
변경 뒤 예상치 못한 회귀 오류 재현 테스트와 핵심 흐름 테스트 추가

테스트 대역은 외부 경계를 분리할 때 사용해요

DB나 외부 결제 서비스에 직접 의존하면 테스트가 느리고 환경 영향을 받습니다. 대역으로 검증 대상 로직과 외부 시스템을 분리하되, 실제 동작과 달라지지 않도록 통합 테스트도 필요해요.

종류역할
Stub정해진 응답 반환
Mock호출 여부와 인자 확인
Fake간단한 실제 동작 제공

단위 테스트는 빠르게 규칙을 확인하고 통합 테스트는 프레임워크와 DB 경계를 점검합니다. 내부 구현보다 외부에서 관찰할 수 있는 동작을 검증하면 리팩터링에 강해져요.

심화

빠르고 믿을 수 있는 테스트 구성

테스트 단계마다 답하는 질문이 달라요

단위 테스트는 작은 로직의 규칙, 통합 테스트는 데이터베이스 같은 경계의 연결, 인수 테스트는 사용자가 기대하는 완성 흐름을 확인합니다. 실행 비용과 변경 위험에 따라 알맞은 층에 테스트를 둡니다. 피라미드 모양을 기계적으로 맞추는 것보다 오류를 빨리 찾고 중요한 동작을 보호하는 편이 중요합니다.

테스트 더블은 외부 의존성을 통제해요

가짜 객체로 외부 서비스 응답을 정하면 빠르고 결정적인 테스트를 만들 수 있습니다. 다만 내부 메서드 호출 횟수만 과하게 검사하면 리팩터링에 약해지므로 중요한 결과와 계약을 확인하세요. 실제 데이터베이스 동작이 중요한 부분은 통합 테스트로 보완합니다.

  • 시간·난수·외부 네트워크를 고정해 결과를 재현합니다.
  • 조건과 기대 결과가 테스트 이름에 드러나게 합니다.
  • 실패 메시지에 입력값과 기대값을 표시합니다.
