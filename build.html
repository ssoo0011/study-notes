빌드와 개발 도구

⚙️

빌드는 코드를 실행 가능한 결과물로 만드는 과정이에요.
테스트와 리소스 복사, 의존성 준비, 패키징까지 포함할 수 있습니다. 프로젝트의 빌드 파일을 읽으면 앱이 어떤 도구와 라이브러리에 기대는지 알 수 있어요.

01

소스 코드에서 실행 결과까지

Java 소스는 컴파일되어 바이트코드가 되고, 라이브러리와 리소스가 준비되어 JAR 같은 배포 파일로 묶일 수 있어요. 빌드 도구는 이 작업의 순서와 옵션을 관리합니다.

소스 .java·설정
→
컴파일 문법 검사
→
테스트 동작 확인
→

→
실행 서버에서 시작

02

Maven과 Gradle: 빌드 규칙 선언하기

Maven과 Gradle은 Java 프로젝트에서 널리 쓰이는 빌드 도구예요. 어떤 소스와 라이브러리를 쓰는지, 무엇을 빌드할지 파일에 기록하고 명령 한 번으로 같은 절차를 실행할 수 있습니다.

비교 Maven Gradle
주 설정 파일 pom.xml build.gradle 또는 Kotlin DSL 파일
표현 XML 중심 Groovy 또는 Kotlin DSL
특징 구조와 규칙이 비교적 정형화 유연한 빌드 로직 작성 가능
공통점 의존성 관리, 테스트, 컴파일, 패키징 자동화

의존성: 다른 사람이 만든 기능 가져오기

라이브러리는 이미 만들어진 기능 묶음이에요. 빌드 도구는 지정된 버전을 내려받고 프로젝트가 사용하도록 연결합니다. 필요한 라이브러리만 추가하고, 직접 관리하는 버전과 라이선스, 알려진 취약점도 살펴야 합니다.

개념 예시 · 빌드 파일에서 라이브러리 선언
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-web")
    testImplementation("org.springframework.boot:spring-boot-starter-test")
}

실제 문법과 사용 가능한 버전은 프로젝트에서 쓰는 Gradle 방식과 Spring Boot 버전에 맞춰 확인하세요.

03

환경 설정: 같은 앱을 다른 장소에서 실행하기

내 컴퓨터, 테스트 서버, 운영 서버는 주소와 비밀 값이 다를 수 있어요. 코드를 환경 값에 맞춰 다시 수정하지 말고 설정 파일이나 환경 변수로 외부에서 값을 받습니다.

비밀 정보를 코드에 적지 않는 예
DB_URL=${DB_URL}
DB_USERNAME=${DB_USERNAME}
DB_PASSWORD=${DB_PASSWORD}

설정에 개발용 데이터베이스 주소가 운영에 반영되는 실수가 없도록 환경별 설정을 검토해요. 비밀번호와 키는 저장소에 올리지 말고 안전한 비밀 저장소에서 공급합니다.

구분 개발 환경 운영 환경
데이터 테스트용·가짜 데이터 실제 사용자 데이터
로그 상세한 진단 정보 민감정보 제거, 적정 수준
비밀 값 개발 전용 키 접근 통제된 운영 키
실행 주소 로컬 또는 검증 서버 사용자 서비스 주소
04

IDE와 터미널: 도구를 이해하며 개발하기

IDE는 코드 편집, 자동 완성, 검색, 디버깅, 빌드를 묶어 제공하는 개발 환경이에요. 터미널은 명령을 직접 실행할 수 있어 자동화와 서버 환경에 유용합니다. 도구가 대신한 작업이 무엇인지 알면 오류를 만났을 때 해결하기 쉬워요.

짧은 피드백 루프

  1. 작은 코드 변경을 합니다.
  2. 컴파일로 기본 오류를 찾습니다.
  3. 관련 테스트를 실행합니다.
  4. 동작을 직접 확인하고 로그를 살핍니다.
  5. 의미 있는 단위로 Git에 기록합니다.

프로젝트의 실행 방법을 README에 적고, 팀원이 새 환경에서도 같은 명령으로 실행 가능한지 확인하세요. 재현이 가능한 빌드는 협업의 중요한 기반입니다.

05

CI와 CD: 반복 확인과 전달 자동화

CI(지속적 통합)는 변경이 저장소에 올라올 때 자동 빌드·테스트를 실행해 문제를 일찍 발견하는 방식이에요. CD는 검증된 변경을 배포 준비하거나 자동 배포하는 흐름을 뜻하며, 조직마다 풀어 쓰는 범위가 다를 수 있습니다.

자동화 파이프라인의 예

변경 공유 Pull Request
→
빌드 의존성·컴파일
→
검사 테스트·분석
→
배포 승인·실행
→
관찰 로그·상태

자동화는 실수를 줄이지만 운영 비밀 값 노출, 잘못된 배포, 데이터 손상 같은 위험을 없애지는 않아요. 배포 승인, 접근 권한, 실패 시 되돌리기 절차를 함께 설계합니다.

다른 컴퓨터에서도 같은 빌드를 만들기

JDK·빌드 도구·의존성·환경 변수가 다르면 같은 소스도 CI에서 다르게 동작할 수 있어요. Wrapper로 빌드 도구를 맞추고 버전을 명시하며 비밀 값은 CI 비밀 저장소로 전달하세요.

  • JDK와 빌드 도구 버전을 고정합니다.
  • CI에서 컴파일·테스트·패키징을 자동 수행합니다.
  • 검증 실패 시 배포를 중단합니다.
  • 결과물에 커밋 식별자를 남겨 배포본을 추적합니다.

캐시는 빌드를 빠르게 하지만 무효화 조건이 부정확하면 오래된 결과를 숨길 수 있어요. CI는 변경을 검증하고 CD는 검증된 결과를 전달하거나 배포합니다.

심화

같은 소스에서 같은 결과를 만드는 빌드

의존성 버전을 고정하고 출처를 살펴요

넓은 버전 범위는 시간이 지나며 다른 라이브러리를 가져올 수 있습니다. 잠금 파일은 실제 해결된 버전을 기록해 개발자 컴퓨터와 CI의 차이를 줄입니다. 직접 의존성과 전이 의존성을 구분하고, 사용하지 않는 패키지는 제거하세요. 외부 패키지의 유지 상태와 알려진 취약점도 확인합니다.

검증한 아티팩트를 환경별로 승격해요

테스트한 결과물을 스테이징과 운영에 그대로 전달하면 환경마다 다시 빌드해서 생기는 차이를 줄일 수 있습니다. 설정과 비밀 값은 실행 환경에서 주입하고 이미지나 저장소에 넣지 않습니다.

  • Wrapper와 JDK 버전을 저장소에 명시합니다.
  • CI에서 깨끗한 체크아웃으로 빌드와 테스트를 실행합니다.
  • 배포 결과물에 버전과 커밋 정보를 남겨 추적과 롤백을 돕습니다.
