01

읽기 쉬운 코드: 다음 사람이 나라고 생각하기

코드는 한 번 쓰고 끝나는 글이 아니라 여러 번 읽고 고치는 작업물이에요. 변수와 함수의 이름이 의도를 드러내고, 한 함수가 하나의 명확한 일을 하며, 주석은 코드만으로 알기 어려운 이유를 설명하면 이해하기 쉽습니다.

어려운 신호 개선 방향 이유
x , data2 역할이 드러나는 이름 사용 맥락을 추측하지 않아도 됨
한 함수가 수십 줄 이름 붙일 수 있는 단계로 분리 실행 흐름과 오류 위치 파악
같은 규칙 복사 변경 이유에 맞춰 공통 로직 정리 한 곳만 고쳐 일관성 유지
주석이 코드 반복 왜 이렇게 했는지 설명 구현보다 결정 배경 공유

추상화를 너무 일찍 만들면 단순한 코드를 복잡하게 만들 수 있어요. 반복과 변경 이유를 관찰한 다음 공통점이 실제로 같은지 확인해 분리합니다.

02

책임 나누기: 응집도는 높이고 결합도는 낮추기

응집도 는 한 모듈 안의 일들이 서로 얼마나 한 목적에 모여 있는지, 결합도 는 다른 모듈의 세부사항에 얼마나 강하게 기대는지에 대한 관점이에요. 보통 관련 책임을 모으고 불필요한 의존을 줄이면 변경이 쉬워집니다.

SOLID를 규칙 암기보다 질문으로

원칙 스스로 물어볼 질문
단일 책임 이 클래스가 바뀌는 이유가 너무 여러 개인가?
개방·폐쇄 새 동작을 추가할 때 안정된 코드를 계속 뜯어고치나?
리스코프 치환 하위 타입을 부모 타입 자리에 써도 약속이 지켜지나?
인터페이스 분리 사용하지 않는 기능까지 구현하도록 강요하나?
의존성 역전 핵심 규칙이 구체적인 외부 세부사항에 묶였나?

SOLID는 모든 클래스를 쪼개라는 명령이 아니에요. 작은 프로그램에 추상 계층을 너무 많이 넣으면 오히려 이해하기 어려워집니다. 바뀌는 이유와 테스트 필요를 기준으로 적용하세요.

03

API 설계: 다른 프로그램이 이해할 계약 만들기

API는 클라이언트와 서버가 요청·응답을 주고받는 약속이에요. 경로, HTTP 메서드, 입력 형식, 성공 결과, 오류와 권한을 일관되게 정하면 프론트엔드와 백엔드가 서로 독립적으로 개발하기 쉬워집니다.

동작 예시 경로 응답 설계
게시글 목록 조회 GET /posts 목록·페이지 정보
게시글 하나 조회 GET /posts/{id} 하나의 게시글 또는 404
게시글 생성 POST /posts 생성 결과와 식별자
게시글 일부 변경 PATCH /posts/{id} 변경 결과
게시글 삭제 DELETE /posts/{id} 삭제 성공·오류 표현

멱등성과 페이지 나누기

멱등성은 같은 요청을 여러 번 적용해도 최종 상태가 같은 성질이에요. 네트워크 재시도로 같은 생성 요청이 중복될 수 있다면 멱등 키 같은 정책을 설계할 수 있습니다. 큰 목록은 페이지 단위로 나누고 최대 크기와 정렬 기준을 명확히 해요.

오류 응답에는 의미 있는 HTTP 상태 코드와 사용자가 이해할 메시지를 담되, 내부 스택 추적이나 비밀 값은 노출하지 않습니다. API 문서에는 인증 방식, 입력 제약, 예시를 함께 기록하세요.

04

구조 선택: 작게 시작하고 복잡해질 때 나누기

한 애플리케이션 안에 기능을 모으는 단일 구조는 개발과 배포가 단순해 시작하기 좋아요. 기능과 팀이 커지면 모듈 경계를 정리하거나 서비스 분리를 고려할 수 있습니다.

디자인 패턴은 문제의 이름이자 선택지

구조·패턴 해결하려는 문제 대가·주의
계층형 웹·업무 규칙·데이터 책임 구분 계층을 무조건 많이 만들지 않기
전략 패턴 선택 가능한 동작 알고리즘 분리 선택과 등록 구조가 추가됨
어댑터 서로 다른 인터페이스를 연결 불필요한 변환 계층 주의
이벤트 기반 발행자와 구독자 결합을 낮춤 흐름 추적과 순서 보장이 어려워짐
마이크로서비스 독립 배포·확장 경계 만들기 네트워크·관찰·데이터 일관성 복잡도 상승

패턴을 이름만 보고 도입하지 마세요. 해결하려는 문제가 실제로 있는지, 추가되는 복잡성이 이득보다 작은지 설명할 수 있어야 합니다.

05

캐시와 일관성: 빠르게 하되 오래된 값 주의

캐시는 비싼 계산이나 조회 결과를 잠시 저장해 응답을 빠르게 할 수 있어요. 하지만 원본 데이터가 변했는데 캐시가 갱신되지 않으면 오래된 결과를 보여 줍니다. 무엇을 얼마나 오래 캐시해도 되는지 먼저 정해야 합니다.

전략 질문 고려할 점
어떤 값을 저장할까? 조회 빈도·계산 비용·개인별 데이터
언제 만료할까? 허용 가능한 오래된 정보 시간
변경 뒤 어떻게 할까? 무효화·갱신·짧은 TTL
캐시가 실패하면? 원본 조회 부하와 장애 전파

성능 최적화는 측정부터 시작하세요. 캐시를 추가하기 전에 느린 요청, 데이터베이스 쿼리, 네트워크 대기 중 무엇이 병목인지 확인합니다.

06

시스템 관점: 실패와 증가를 예상하기

시스템 설계는 구성 요소를 늘리는 것만이 아니에요. 얼마나 많은 요청을 처리할지, 한 부분이 실패하면 어떻게 되는지, 데이터를 잃지 않으려면 어떤 복구가 필요한지 요구사항을 구체화하는 과정입니다.

관찰 가능성: 로그·메트릭·추적

신호 보여 주는 것 질문
로그 시간순 사건과 오류 요청 처리 중 어떤 일이 일어났나?
메트릭 숫자로 집계한 상태 응답 시간·요청량·오류율이 어떻게 변했나?
분산 추적 여러 서비스에 걸친 한 요청의 흐름 어느 구간에서 오래 기다렸나?

확장성, 가용성, 비용은 서로 영향을 줘요. 사용자 규모와 장애 허용 기준을 먼저 정하고, 실제로 필요한 만큼 복잡한 구성을 선택합니다.

변경 가능한 구현을 약속 뒤에 숨기기

업무 로직이 이메일 전송 클래스에 직접 의존하면 SMS로 바꿀 때 업무 코드까지 고쳐야 합니다. 필요한 동작을 인터페이스로 표현하면 상위 정책이 구현 세부사항과 분리돼요.

의존성 주입으로 구현 분리
interface MessageSender {
    void send(String message);
}
class AlertService {
    private final MessageSender sender;
    AlertService(MessageSender sender) { this.sender = sender; }
    void alert(String text) { sender.send(text); }
}

테스트에서는 가짜 sender를 넣고 운영에서는 실제 구현을 연결할 수 있습니다. 추상화는 변경 경계를 분리할 실익이 있을 때 도입하고, 높은 응집도와 낮은 결합도를 목표로 하세요.

심화

변경하기 쉬운 설계를 만드는 기준

응집도는 높이고 결합도는 낮춰요

응집도는 한 모듈의 기능이 하나의 목적에 모인 정도이고 결합도는 다른 모듈의 내부 변경에 영향을 받는 정도입니다. 저장·검증·출력을 한 클래스가 모두 맡으면 작은 수정도 여러 책임에 번집니다. 역할을 나누고 안정적인 인터페이스로 연결하면 테스트와 구현 교체가 쉬워집니다.

SOLID는 설계 선택을 점검하는 질문이에요

단일 책임은 변경 이유가 하나인지, 개방 폐쇄는 기존 코드를 매번 고치지 않고 확장할 수 있는지 묻습니다. 의존 역전은 정책 코드가 구체 구현에 직접 묶이지 않게 돕습니다. 원칙을 기계적으로 적용하면 추상화가 지나치게 늘 수 있으므로 실제 변경 요구와 테스트 비용을 기준으로 판단하세요.

  • 복잡한 선택은 데이터 흐름과 책임 경계를 그려 봅니다.
  • 중요한 설계 결정과 이유를 짧게 기록합니다.
  • 변화 이유가 다른 코드를 억지로 하나로 합치지 않습니다.
