Git 협업

🕰️

Git은 “저장” 버튼보다 자세한 시간 여행 기록에 가까워요.
작업한 내용을 의미 있는 단위로 기록하고, 기록 사이의 차이를 확인하고, 팀원의 작업을 안전하게 합치는 도구입니다.

01

버전 관리: 변경 이유와 결과를 기록하기

프로젝트 폴더를 통째로 복사해 final_final2_reallyfinal 같은 폴더를 만드는 대신, Git은 파일의 변경 사항을 버전으로 저장합니다. 저장소(repository)는 프로젝트와 그 변경 기록이 들어 있는 공간이에요.

작은 기록 단위, 커밋

커밋(commit)은 특정 시점의 변경을 설명과 함께 기록한 묶음이에요. Git은 모든 순간의 파일 전체를 복사하는 것처럼 보이지만, 내부적으로 효율적인 방식으로 내용을 저장하고 이전 상태와 비교할 수 있게 합니다.

가장 자주 쓰는 기본 흐름
git status                 # 현재 변경 확인
git add src/Main.java      # 기록에 넣을 변경 선택
git diff --staged          # 기록될 차이 다시 확인
git commit -m "회원 조회 추가" # 이력에 저장

작업 디렉터리에서 파일을 고친 뒤, add 로 이번 커밋에 담을 내용을 스테이징하고, commit 으로 기록합니다. add 후에도 파일을 다시 확인하면 기록에 실수로 비밀 값이 들어가는 일을 줄일 수 있어요.

영역 뜻 확인 방법
작업 디렉터리 지금 수정하고 있는 파일 git status
스테이징 영역 다음 커밋에 포함하겠다고 고른 변경 git diff --staged
저장소 이력 이미 만든 커밋들의 기록 git log --oneline
02

브랜치: 평행한 작업 줄기를 만들기

브랜치는 커밋을 가리키는 가벼운 이름표예요. 새 기능을 만들 때 브랜치를 나누면 기존 안정 버전에 영향을 덜 주면서 작업할 수 있습니다.

main 기준 버전
↘
feature 새 기능 작업
→
검토 변경 비교
→
병합 기준에 통합
브랜치 만들고 이동하기
git switch -c feature/member-search
git status
# 작업하고 커밋한 뒤
 git switch main
git merge feature/member-search

병합과 충돌

병합(merge)은 다른 브랜치의 변경을 현재 브랜치에 합칩니다. 같은 파일의 같은 부분을 서로 다르게 바꾸면 Git이 자동으로 결정하지 못하고 충돌(conflict)을 표시해요. 사람이 의도한 최종 내용을 정하고, 관련 테스트를 한 뒤 해결된 파일을 다시 커밋해야 합니다.

상황 Git의 반응 내가 할 일
서로 다른 파일 수정 대개 자동 병합 변경이 함께 잘 동작하는지 확인
같은 부분을 다르게 수정 충돌 표시 두 의도를 읽고 최종 코드 작성
병합 뒤 기능 깨짐 텍스트 충돌은 없을 수도 있음 테스트와 실행 결과 확인
03

원격 저장소: 내 컴퓨터와 팀의 저장소 연결하기

로컬 저장소는 내 컴퓨터에 있고, 원격(remote) 저장소는 GitHub 같은 서버에 있어요. push 는 내 커밋을 원격으로 보내고, fetch 는 원격 이력을 확인하며, pull 은 원격 변경을 가져와 현재 작업과 통합하는 명령입니다.

내 브랜치커밋 push → 원격 저장소팀과 공유 ← pull 팀 브랜치변경 가져오기

팀 작업의 기본 흐름

  1. 최신 기준 브랜치에서 새 작업 브랜치를 만듭니다.
  2. 작은 단위로 수정하고, 의도가 드러나는 커밋을 만듭니다.
  3. 원격 브랜치에 push한 뒤 Pull Request(PR)를 엽니다.
  4. 동료 피드백과 자동 검사를 확인하고 수정합니다.
  5. 검토가 끝난 변경을 기준 브랜치에 병합합니다.

여러 사람이 같은 줄기를 동시에 고치므로, push 전 원격의 최신 변경을 확인하고 필요하면 통합합니다. 정확한 팀 규칙은 프로젝트에 따라 달라요.

명령 하는 일 주의
fetch 원격 변경을 가져와 비교 가능하게 함 현재 작업 내용을 자동으로 합치지 않음
pull 원격 변경을 가져와 통합 충돌이 생길 수 있음
push 내 커밋을 원격에 올림 팀 이력을 덮는 강제 push 주의
04

되돌리기: 명령 전에 상태와 공유 여부 확인하기

Git에서 되돌리는 방법은 작업이 커밋됐는지, 이미 다른 사람과 공유했는지에 따라 달라져요. 특히 공유한 이력을 강제로 바꾸면 팀원의 작업과 충돌할 수 있습니다.

상황에 따라 고르는 복구 명령

상태 목표 일반적인 도구
아직 스테이징 전 작업 내용 비교 git diff
스테이징했지만 커밋 전 선택에서 제외 git restore --staged
로컬 커밋을 되돌림 변경을 보존하며 수정 git revert 또는 신중한 reset
이미 공유한 커밋 취소 이력을 새로 남김 git revert 가 보통 안전

명령을 실행하기 전 git status 와 git log 로 상황을 확인하고, 중요한 변경은 별도로 복사하거나 백업하세요. 강제 옵션은 의미를 모르면 사용하지 않습니다.

05

코드 리뷰: 변경을 이해하고 함께 품질 높이기

Pull Request는 변경을 팀원에게 보여 주고, 토론·검사·승인을 거쳐 통합하는 협업 절차예요. 특정 서비스의 버튼 이름이 아니라, 변경 검토를 위한 작업 단위라고 이해하면 됩니다.

읽기 좋은 변경 기록

좋은 습관 왜 도움이 되나? 예
작은 커밋 변경 의도를 빠르게 파악 “회원 검색 조건 추가”
설명 있는 PR 배경과 확인 방법 공유 무엇을 왜 바꿨는지 작성
비밀 값 검사 토큰·비밀번호 노출 예방 커밋 전 diff 확인
검사 결과 확인 통합 전 실수 발견 테스트·빌드 통과 확인

리뷰는 사람에 대한 평가가 아니라 변경 사항과 위험을 살펴보는 과정이에요. 질문과 제안은 구체적으로 쓰고, 작성자는 맥락과 의도를 설명합니다.

변경을 되돌릴 때 공유 여부부터 확인해요

작업 파일 수정, 스테이징, 커밋은 서로 다른 상태입니다. 먼저 git status, git diff, git diff --staged로 무엇이 바뀌는지 확인하세요.

상황방향
스테이징 해제git restore --staged 파일
공유 전 커밋 수정상태를 확인한 뒤 reset 검토
공유된 커밋 취소git revert 해시로 새 취소 커밋 기록

reset은 브랜치 위치를 옮기고 옵션에 따라 스테이징과 파일에도 영향을 줍니다. 공유된 이력을 강제로 다시 쓰면 동료 작업과 충돌할 수 있어요.

안전한 습관 되돌리기 전에 영향을 받는 파일과 커밋을 확인하고 필요한 변경은 따로 저장하세요.

심화

협업에서 이력을 안전하게 합치기

merge와 rebase는 이력을 다르게 남겨요

merge는 두 이력을 합친 시점을 기록하고, rebase는 현재 브랜치의 커밋을 새 기준 위에 다시 적용해 선형 이력을 만듭니다. rebase는 커밋 기록을 바꾸므로 이미 다른 사람이 가져간 공유 커밋에는 사용하지 않는 편이 안전합니다.

충돌은 양쪽 변경의 의도를 읽고 풀어요

충돌 표시는 같은 부분이 다르게 바뀌어 Git이 선택하지 못했다는 뜻입니다. 한쪽을 무조건 고르지 말고 두 변경의 목적을 확인해 합친 뒤 diff와 관련 동작을 살펴보세요. 진행 중 취소 명령을 알아 두면 잘못된 통합에서 되돌아오기 쉽습니다.

  • 작업 상태를 확인하고 작은 단위로 커밋합니다.
  • 메시지에는 변경 이유와 맥락을 남깁니다.
  • 비밀 값이 올라가면 커밋 삭제뿐 아니라 해당 자격 증명도 폐기합니다.
