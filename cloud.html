클라우드는 “다른 사람 컴퓨터”라는 설명만으로는 부족해요.
네트워크, 사용자 권한, 배포, 데이터 보관과 비용까지 설정해야 안전한 서비스가 됩니다. 공급자가 관리하는 부분과 우리가 관리할 부분을 구분하세요.

01

클라우드 서비스: 컴퓨터와 관리 책임 빌리기

클라우드 서비스는 서버와 데이터센터 자원을 네트워크로 제공해요. 가상 머신, 컨테이너 실행 환경, 객체 저장소, 관리형 데이터베이스 같은 서비스를 조합할 수 있습니다.

IaaS·PaaS·SaaS의 차이

모델 공급자가 더 많이 관리 사용자가 주로 관리 예를 들면
IaaS 물리 장비·가상화 OS·런타임·앱·데이터 가상 서버
PaaS OS·런타임 일부까지 애플리케이션·데이터 관리형 앱 실행 환경
SaaS 애플리케이션 운영 대부분 사용자·데이터 설정 웹 기반 협업 도구

이 구분은 이해를 돕는 모델이며 각 공급자 서비스의 실제 책임 범위는 계약과 기능에 따라 확인해야 해요.

02

클라우드 네트워크: 서비스에 닿는 길 설계

가상 네트워크 안에 서브넷을 나누고 라우팅과 방화벽 규칙을 설정합니다. 공개로 접근할 웹 입구와 내부에서만 접근할 앱·데이터베이스를 분리해 공격 표면을 줄여요.

인터넷에 모두 공개할 필요는 없어요

인터넷사용자 → 공개 진입점LB·Proxy → 앱 서브넷앱 서버 → DB 서브넷내부 접근
대상 필요한 접근 예 기본 원칙
웹 진입점 인터넷에서 HTTPS 공개 포트 최소화
애플리케이션 진입점에서 앱 포트 직접 인터넷 공개 제한
데이터베이스 필요한 앱 서버에서 DB 포트 공개 IP 없이 내부 접근
관리 접속 승인된 관리자 경로 강한 인증과 접속 기록

이름이 낯선 서버들: 어떤 일을 하고 언제 쓸까요?

아래 이름은 꼭 별도 가상 머신 한 대를 뜻하지 않아요. 직접 서버로 운영할 수도 있고, 클라우드의 관리형 서비스로 같은 역할을 맡길 수도 있습니다. 서버를 둘 때는 필요한 통신 경로만 열고, 가능하면 인터넷에 직접 노출하지 않습니다.

이름하는 일언제 쓰나흔한 배치·접근
Bastion host
(점프 서버)		관리자가 내부 서버에 접속할 때 거치는 통제 지점사설 서브넷의 VM을 SSH/RDP로 관리해야 할 때관리자 인증을 제한하고 기록을 남김. 내부 서버는 bastion에서 오는 관리 포트만 허용. 가능하면 세션 관리형 접속을 사용
NFS 서버여러 Linux 서버가 함께 쓰는 네트워크 파일 시스템 제공여러 앱 인스턴스가 같은 업로드 파일이나 공유 디렉터리를 읽고 써야 할 때사설 네트워크에 배치하고 앱 서버에서만 NFS 포트를 허용. 단일 서버는 장애 지점이 될 수 있어 관리형 파일 스토리지나 이중화를 검토
Load Balancer (LB)들어온 요청을 여러 서버로 분배하고 상태가 나쁜 서버를 제외앱 서버를 여러 대 운영하거나 배포·장애 시 트래픽을 나눠야 할 때인터넷용은 공개 구간, 내부 서비스용은 사설 구간에 배치 가능
Reverse Proxy앱 앞에서 요청을 전달하고 TLS 종료, 경로 기반 분기 등을 처리여러 앱을 도메인·경로로 나누거나 앱 서버를 외부에 직접 공개하지 않을 때공개 진입점 또는 LB 뒤에 배치. LB와 기능이 겹칠 수 있어 역할을 구분
NAT Gateway사설 서버가 외부로 나가는 연결을 중계사설 앱 서버가 패키지 업데이트나 외부 API 호출은 해야 하지만 외부에서 먼저 접속하게 하고 싶지 않을 때공개 서브넷의 NAT 장치로 아웃바운드 경로를 설정. 인바운드 접속 통로는 아님
DNS 서버도메인 이름을 IP 주소로 찾고 내부 이름을 관리서비스 주소를 이름으로 연결하거나 내부 도메인을 운영할 때대개 클라우드 관리형 DNS를 사용. 내부·외부 조회 범위를 구분
캐시 서버 (Redis 등)자주 쓰는 데이터를 메모리에 보관해 빠르게 제공세션, 짧은 수명의 조회 결과, 작업 상태를 여러 앱 인스턴스가 공유할 때사설 네트워크에 두고 앱에서만 접근. 캐시는 원본 데이터베이스의 백업을 대신하지 않음
메시지 브로커 / 큐서비스 사이에 작업을 전달하고 소비자가 나중에 처리하도록 대기메일 발송·이미지 처리처럼 오래 걸리는 작업을 웹 요청과 분리하거나 일시적 부하를 흡수할 때관리형 큐 또는 브로커를 쓰고 생산자·소비자 권한과 재시도·중복 처리를 설계
모니터링·로그 수집기서버 상태, 메트릭, 로그를 모아 검색·경보에 사용장애 원인을 찾고 용량·오류·보안 이벤트를 확인할 때중앙 관리형 관찰 서비스로 전송하는 구성이 흔함. 민감정보와 보관 기간을 관리

예시 경로: 인터넷 → 공개 LB → 사설 앱 서버 → 내부 DB. 관리자는 별도의 승인된 경로로 bastion 또는 세션 관리 기능을 거쳐 접속하고, 앱 서버는 사설 NFS·캐시·큐에 필요한 포트로만 연결합니다.

03

IAM: 누가 무엇을 할 수 있는지 관리하기

IAM은 사용자·서비스 계정·역할에 어떤 리소스 작업을 허용할지 관리하는 체계예요. 앱이 객체 저장소를 읽기만 한다면 삭제 권한까지 주지 않는 최소 권한 원칙이 중요합니다.

  1. 사람 계정과 앱이 사용하는 서비스 계정을 구분합니다.
  2. 필요한 리소스와 동작만 허용합니다.
  3. 관리자 계정에는 강한 인증을 요구합니다.
  4. 임시 자격 증명과 키 교체 방식을 고려합니다.
  5. 권한 변경과 접근 기록을 주기적으로 확인합니다.

클라우드 계정 키가 Git 저장소에 올라가면 외부인이 자원을 생성하거나 데이터를 읽을 수 있어요. 비밀 관리 기능을 쓰고, 노출된 키는 즉시 폐기·교체합니다.

04

가용성과 확장: 한 서버에 모든 걸 맡기지 않기

로드 밸런서는 여러 앱 서버에 요청을 분배하고 상태가 나쁜 서버를 제외할 수 있어요. 자동 확장은 사용량에 맞춰 실행 인스턴스를 늘리거나 줄입니다. 다만 데이터 저장 위치와 세션 상태를 함께 설계하지 않으면 서버를 늘려도 기능이 깨질 수 있습니다.

장애는 완전히 없애기보다 영향 줄이기

위험 완화 방법 함께 볼 것
서버 한 대 중단 여러 인스턴스·상태 확인 세션·파일 공유
한 가용 구역 장애 복수 영역 분산 데이터 복제·비용
DB 장애 관리형 복구·백업 복원 목표와 테스트
급격한 트래픽 자동 확장·요청 제한 DB와 외부 API 용량

복제와 이중화는 가용성을 높일 수 있지만 구성·비용·데이터 일관성을 복잡하게 합니다. 필요한 서비스 수준을 정하고 그에 맞게 선택합니다.

05

관찰과 비용: 사용량은 숫자로 나타나요

클라우드 비용은 실행 시간, 저장 공간, 요청량, 데이터 전송량 등에 따라 달라질 수 있어요. 사용하지 않는 서버와 저장소, 과도한 로그 보관도 비용을 만들 수 있습니다.

로그·메트릭과 예산 알림

운영 비용 경보를 설정하고, 태그나 프로젝트 단위로 비용을 추적하세요. 비용 절감 때문에 보안·백업·장애 복구를 없애지 않도록 균형을 잡아야 합니다.

장애 복구와 비용을 함께 설계하기

백업과 고가용성은 역할이 달라요

여러 가용 영역에 서비스를 배치하면 한 영역 장애를 견디는 데 도움이 되지만 잘못 삭제한 데이터를 복구해 주지는 않습니다. 백업은 특정 시점의 데이터를 되살리는 수단입니다. RPO는 허용 가능한 데이터 손실 범위, RTO는 복구에 허용되는 시간입니다. 실제 복원 훈련으로 절차와 시간을 확인해야 합니다.

비용은 컴퓨팅 외에도 쌓여요

저장 공간, 요청 수, 데이터 전송, 로그 보관, 관리형 서비스 요금도 확인합니다. 개발 자원은 사용하지 않을 때 중지하고, 로그 보관 기간과 자원별 예산 알림을 설정하세요.

  • 서비스별 장애 영향과 복구 순서를 문서화합니다.
  • 공개 주소와 관리자 권한은 필요한 자원에만 부여합니다.
  • 비용 태그로 팀·서비스별 사용량을 살핍니다.
