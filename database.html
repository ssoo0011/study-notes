데이터베이스와 SQL

🗄️

데이터는 한 번 잃으면 되돌리기 어려울 수 있어요.
실제 데이터를 수정하는 쿼리는 대상과 조건을 확인하고, 중요한 변경은 트랜잭션과 백업 계획을 생각한 뒤 실행하세요.

01

관계형 데이터베이스: 표로 사실을 정리하기

관계형 데이터베이스는 데이터를 테이블(표), 행(row), 열(column)로 표현해요. 각 테이블은 한 종류의 대상을 정리하고, 키를 통해 다른 테이블과 관계를 맺습니다.

기본키와 외래키

기본키 는 행 하나를 구별하는 값이고, 외래키 는 다른 테이블의 행을 가리키는 값이에요. 예를 들어 주문 테이블이 회원 ID를 저장하면, 주문과 회원을 연결할 수 있습니다.

members orders
id (기본키) ← 연결 ← member_id (외래키)
name total_price
email created_at

데이터베이스 제약 조건은 잘못된 데이터를 저장하지 못하게 도와요. 예를 들어 외래키는 존재하지 않는 회원을 가리키는 주문을 제한할 수 있습니다.

02

SQL 조회: 필요한 행과 열 고르기

SQL은 관계형 데이터베이스에 원하는 작업을 설명하는 언어예요. SELECT 로 열을 고르고, FROM 으로 테이블을 지정하며, WHERE 로 조건을 걸 수 있습니다.

조건에 맞는 회원 조회
SELECT id, name
FROM members
WHERE status = 'ACTIVE'
ORDER BY created_at DESC
LIMIT 20;

JOIN: 관련된 여러 표 이어 보기

회원 이름과 주문 금액은 다른 테이블에 저장할 수 있어요. JOIN은 공통 키를 기준으로 관련 행들을 이어서 조회합니다.

주문과 회원 이름 함께 보기
SELECT m.name, o.total_price
FROM orders o
JOIN members m ON m.id = o.member_id
WHERE o.id = 42;

조회에 필요하지 않은 모든 열을 무작정 가져오지 말고, 어떤 조건과 정렬이 필요한지 명확히 하세요. 서비스가 커지면 쿼리 성능과 접근 권한도 중요합니다.

03

데이터 변경과 제약 조건

INSERT 는 추가, UPDATE 는 수정, DELETE 는 삭제예요. 변경 쿼리에서 WHERE 를 빠뜨리면 의도보다 많은 행을 바꿀 수 있으므로 실행 대상부터 먼저 확인합니다.

안전한 변경 전, 같은 조건으로 조회해 보기
SELECT id, status FROM orders WHERE id = 42;

UPDATE orders
SET status = 'PAID'
WHERE id = 42;

제약 조건은 데이터 규칙을 지켜요

제약 조건 의미 예
PRIMARY KEY 각 행을 구분하는 고유 식별 회원 ID 중복 불가
FOREIGN KEY 다른 테이블 데이터와 관계 확인 없는 회원의 주문 제한
NOT NULL 값을 반드시 제공 주문 날짜 필수
UNIQUE 중복 값 제한 이메일 중복 금지
CHECK 값의 조건 확인 수량이 0 이상
04

테이블 설계와 정규화: 중복과 불일치 줄이기

회원 이름을 모든 주문 행에 복사하면 이름 변경 때 여러 곳을 고쳐야 해요. 일부만 바뀌면 서로 다른 이름이 남습니다. 정규화는 데이터 중복과 갱신 문제를 줄이도록 테이블 구조를 나누고 관계를 정리하는 과정입니다.

대상을 나누되 관계는 키로 표현

설계 질문 생각해 볼 점 좋은 방향
이 행은 어떤 대상을 나타내나? 회원 정보와 주문 정보가 섞였나? 한 테이블은 한 주제에 집중
값이 반복되나? 주소·이름이 여러 행에 복제되나? 반복 데이터 분리 검토
어떤 값으로 연결하나? 이름 변경에 영향을 받나? 안정적인 식별 키 사용

정규화만 무조건 많이 하는 것이 목표는 아닙니다. 읽기 성능이나 사용 패턴 때문에 의도적으로 중복을 두는 경우도 있지만, 일관성 유지 비용을 이해하고 선택해야 해요.

05

인덱스: 자주 찾는 데이터를 빨리 찾는 안내표

인덱스는 특정 열을 기준으로 데이터를 더 빨리 찾도록 도와주는 자료구조예요. 책 뒤의 찾아보기처럼 필요한 위치를 빨리 찾을 수 있지만, 인덱스를 만들고 갱신하는 데 저장 공간과 쓰기 비용이 듭니다.

실행 계획으로 실제 접근 방식 확인

상황 인덱스 효과 주의점
자주 검색하는 열 조회 범위를 줄일 수 있음 데이터와 쿼리로 효과 확인
행이 매우 적은 테이블 전체 읽기가 더 단순할 수 있음 인덱스가 항상 빠르진 않음
자주 바뀌는 열 갱신 비용이 추가 필요한 인덱스만 유지
복합 조건 검색 열 순서가 중요할 수 있음 실행 계획·실제 성능 측정

성능 문제는 추측만으로 인덱스를 추가하기보다 느린 쿼리를 측정하고 실행 계획을 확인해 원인을 찾습니다.

06

트랜잭션: 함께 성공해야 하는 데이터 작업 묶기

계좌 송금처럼 여러 변경이 한 묶음으로 성공해야 하는 작업을 트랜잭션으로 처리해요. 중간에 실패하면 변경 전체를 취소해 데이터가 반만 적용된 상태가 되지 않게 합니다.

ACID와 동시에 발생한 변경

속성 쉽게 말하면
Atomicity 전부 적용하거나 전부 취소
Consistency 작업 전후 데이터 규칙 유지
Isolation 동시 작업의 간섭을 제어
Durability 성공한 결과를 지속적으로 보존

동시에 재고를 차감하는 요청이 오면 잠금·격리 수준 같은 데이터베이스 기능이 중요해져요. 강한 격리는 충돌을 줄일 수 있지만 처리량을 낮출 수도 있으므로 데이터베이스와 업무에 맞게 선택해야 합니다.

07

접근 권한과 백업: 저장된 정보 지키기

애플리케이션 계정에는 필요한 테이블과 작업만 허용하세요. DB를 인터넷에 그대로 공개하지 않고, 비밀번호와 접속 주소는 안전하게 관리하며, 개인정보를 테스트 환경으로 옮길 때도 보호 조치를 해야 합니다.

백업 주기와 보관 위치를 정하고 실제 복구 테스트를 해야 해요. 백업 파일을 만든 사실만으로 복구가 보장되지는 않습니다.

인덱스는 조회를 돕지만 갱신 비용이 있어요

인덱스는 값을 찾기 좋은 구조로 정리해 행을 빨리 찾도록 돕습니다. 저장 공간을 쓰고 INSERT·UPDATE·DELETE 때 갱신해야 하므로 많을수록 좋은 것은 아니에요.

복합 인덱스와 실행 계획
CREATE INDEX idx_orders_customer_date
ON orders (customer_id, created_at);
EXPLAIN SELECT order_id, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at;

복합 인덱스의 열 순서는 중요합니다. customer_id 조건에는 적합하지만 created_at만 검색하면 같은 효과가 없을 수 있어요. 실행 계획에서 접근 경로와 예상 행 수를 확인하세요.

튜닝 순서 느린 쿼리를 측정하고 실행 계획을 본 뒤 인덱스를 조정하고 다시 측정합니다.

심화

트랜잭션과 인덱스로 데이터의 일관성을 지키기

격리 수준은 동시 작업의 균형이에요

동시에 실행되는 트랜잭션이 서로의 변경을 어떻게 볼지 격리 수준으로 정합니다. 격리가 약하면 아직 확정되지 않은 값이나 조회 결과 변동이 생길 수 있고, 강하면 대기와 충돌 비용이 커질 수 있습니다. 재고 차감처럼 한 규칙을 지켜야 하는 여러 작업은 트랜잭션으로 묶고 실패할 때 전체가 되돌아가는지 확인합니다.

인덱스는 읽기를 돕고 쓰기 비용을 더해요

인덱스는 행을 빠르게 찾게 해 주지만 저장 공간을 쓰고 데이터 변경 때 갱신됩니다. 실제 검색 조건·조인·정렬 패턴에 맞춰 만들고 실행 계획으로 전체 테이블 스캔 여부와 예상 행 수를 확인하세요. 복합 인덱스는 열의 순서도 중요합니다.

  • 기본 키와 외래 키로 관계와 중복을 관리합니다.
  • 자주 쓰는 쿼리를 기준으로 인덱스를 설계합니다.
  • 백업 복원과 스키마 변경 절차를 준비합니다.
