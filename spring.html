추리 질문 각 객체에 한 가지 책임을 맡기고, 필요한 객체끼리 연결하면 어떤 점이 좋아질까요?

Spring은 객체를 만들고 연결하는 일을 도와주며, 웹 요청을 Controller에 연결하고, 애플리케이션의 역할에 따라 Service와 Repository 등을 나눌 수 있게 합니다. 각 역할을 분리하면 테스트와 변경이 쉬워지고, 한 기능의 흐름도 읽기 편해집니다.

01

Spring 만나기: 반복되는 기반 작업을 맡기는 프레임워크

프레임워크 는 프로그램의 기본 구조와 반복 작업을 제공하고, 개발자가 그 틀 안에 필요한 코드를 채우도록 돕는 도구예요. Spring Framework는 Java 애플리케이션을 만들기 위한 큰 생태계입니다.

Spring이 객체를 관리하고, 웹 요청을 연결하고, 데이터 접근과 트랜잭션 같은 기능을 도와요. 그렇다고 비즈니스 규칙까지 알아서 정해 주는 것은 아닙니다. 무엇을 만들지와 업무 규칙은 개발자가 설계해야 해요.

Spring Boot는 무엇을 쉽게 해 줄까요?

Spring Boot는 Spring 애플리케이션을 빠르게 시작하고 실행하도록 설정과 편의 기능을 제공해요. 자주 함께 쓰는 라이브러리를 묶어 선택을 단순화하고, 내장 서버로 별도의 웹 서버 설치 과정 없이 개발용 앱을 실행할 수 있게 도와줍니다.

이름 하는 일 비유
Java 애플리케이션 코드를 작성하는 언어 요리법을 쓰는 말
Spring Framework 객체 관리·웹·데이터 기능의 기반 주방과 조리 도구
Spring Boot 설정과 실행을 단순하게 도와줌 기본 준비가 된 조리 세트
라이브러리 필요할 때 코드에서 불러 쓰는 기능 필요할 때 꺼내 쓰는 도구

초보자의 관점 시작은 Spring Boot 프로젝트로 하더라도, 뒤에서 작동하는 Spring 개념(IoC, DI, MVC, Bean 등)을 알면 코드가 왜 동작하는지 이해할 수 있어요.

02

IoC와 DI: 객체를 직접 만들고 연결하는 일을 맡기기

일반적인 Java 코드에서는 필요한 객체를 new 로 직접 만들 수 있어요. 객체가 많아지면 누가 무엇을 만들고 서로 연결할지 관리하기 어렵습니다.

IoC (제어의 역전)는 객체의 생성과 연결을 애플리케이션 코드가 매번 직접 결정하지 않고, 프레임워크가 관리하도록 맡기는 생각이에요. DI (의존성 주입)는 필요한 객체를 외부에서 전달받아 사용하는 방법입니다.

생성자 주입 · 필요한 협력 객체를 전달받기
@Service
class OrderService {
    private final OrderRepository orderRepository;

    OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}

위 코드는 설명용 조각이에요. Spring이 관리하는 OrderRepository 객체를 준비해 생성자에 전달할 수 있습니다.

Bean과 컨테이너

Bean 은 Spring 컨테이너가 생성하고 관리하는 객체예요. 컨테이너는 Bean들을 보관하고 필요한 관계를 연결합니다. 클래스에 @Service , @Repository , @Component 등을 붙이면 설정에 따라 Bean으로 등록될 수 있어요.

Repository데이터 처리 역할 등록 → Spring 컨테이너객체 생성·관리 주입 → Service필요한 객체 사용
개념 질문에 답해 보기 한 줄 정리
의존성 이 클래스가 일을 하려면 무엇이 필요한가? 다른 객체에 기대어 사용하는 관계
DI 필요한 객체를 어떻게 받는가? 외부에서 필요한 객체를 전달받음
Bean Spring이 관리하는 객체인가? 컨테이너가 생성·관리하는 객체
컨테이너 객체 생성과 연결을 누가 관리하는가? Bean과 의존 관계를 관리하는 공간

생성자 주입은 필요한 의존성을 숨기지 않고, 객체가 만들어진 뒤 바뀌지 않게 하기 쉬워 많이 사용합니다. 무조건 모든 클래스를 Bean으로 만들기보다, 프레임워크가 관리할 필요가 있는 객체만 등록해요.

03

웹 요청 받기: MVC와 Controller

Spring MVC는 웹 요청을 받아 적절한 코드로 연결하고 결과를 응답으로 만드는 구조예요. Controller 는 HTTP 요청과 응답을 담당하는 입구 역할을 합니다.

간단한 REST API

GET /hello 요청에 JSON으로 응답하는 예시
@RestController
class HelloController {
    @GetMapping("/hello")
    HelloResponse hello() {
        return new HelloResponse("안녕하세요");
    }
}

record HelloResponse(String message) {}

@RestController 는 메서드의 반환값을 응답 데이터로 쓰는 Controller를 표시해요. @GetMapping 은 GET 방식의 특정 경로 요청을 연결합니다. 세부 동작은 설정과 버전에 따라 달라질 수 있어요.

HTTP 요청GET /hello → DispatcherServlet요청 전달 창구 → Controller경로에 맞는 메서드

Spring MVC에서는 보통 앞단의 DispatcherServlet 이 요청을 받고, 등록된 경로와 Controller를 찾아 전달해요. Controller가 결과를 반환하면 Spring이 HTTP 응답으로 만들어 돌려줍니다.

HTTP 동작 흔한 의미 Spring 매핑 예
GET 데이터 조회 @GetMapping
POST 새 데이터 생성 요청 @PostMapping
PUT 전체 교체 성격의 수정 @PutMapping
PATCH 일부 수정 @PatchMapping
DELETE 삭제 요청 @DeleteMapping

HTTP 메서드는 요청의 목적을 표현하는 관례예요. 실제 API에서는 권한, 입력값, 중복 요청 등을 함께 고려해야 합니다.

04

역할 나누기: Controller·Service·Repository

Controller 하나에 HTTP 처리, 업무 규칙, SQL, 응답 변환을 모두 넣으면 코드가 금방 복잡해져요. 기능에 따라 역할을 나누면 각 부분을 이해하고 테스트하기 쉬워집니다.

Controller 웹 요청·응답
↓
Service 업무 규칙·흐름
↓
Repository 데이터 저장·조회
↓
Database 영속 데이터
계층 주요 책임 하지 않도록 조심할 일
Controller 요청 해석, 입력 전달, HTTP 응답 선택 복잡한 업무 규칙을 전부 직접 처리
Service 업무 규칙과 여러 작업의 순서 조정 웹 요청 세부사항에 과하게 의존
Repository 데이터 저장·조회 방법 제공 화면 응답 형식이나 업무 흐름 결정
Database 데이터를 지속적으로 보관 앱의 모든 규칙을 대신 판단

DTO와 Entity를 왜 나눌까요?

DTO 는 계층 사이에서 주고받을 데이터를 담는 객체예요. Entity 는 보통 데이터베이스 테이블과 연결되는 도메인 객체입니다. 둘을 나누면 외부에 보여 줄 정보와 데이터베이스 상태를 별도로 다룰 수 있어요.

요청 데이터와 내부 데이터는 목적이 달라요
record CreatePostRequest(String title, String content) {}
record PostResponse(Long id, String title) {}

// Entity에는 내부 식별자, 생성 시각 등 저장 상태가 더 있을 수 있음

Entity를 그대로 API 응답에 내보내면 내부 필드 노출, 순환 참조, 데이터 구조 변경 영향이 생길 수 있어요. 모든 경우에 DTO가 반드시 별도여야 하는 것은 아니지만, 외부 API와 내부 저장 모델의 책임 차이를 생각해 결정합니다.

05

데이터 저장: Repository와 JPA

애플리케이션이 종료돼도 남아야 하는 데이터는 데이터베이스에 저장합니다. Repository는 데이터를 저장하거나 찾는 작업을 애플리케이션이 사용할 수 있도록 감싸는 역할이에요.

JPA는 Java 객체와 관계형 데이터베이스를 연결하는 표준 명세이고, Hibernate는 널리 쓰이는 JPA 구현체예요. Spring Data JPA는 Repository 작성과 데이터 접근을 더 편하게 도와주는 Spring 프로젝트입니다.

이름 무엇인가요? 관계
JPA Java 객체와 관계형 DB를 다루는 표준 규약 사용 방식의 명세
Hibernate JPA 규약을 실제로 구현한 ORM JPA 구현체
Spring Data JPA Spring에서 Repository 작업을 돕는 도구 JPA를 편리하게 사용
Repository 데이터 저장·조회 인터페이스 Service가 데이터 작업 요청
Repository로 게시글 찾기
interface PostRepository extends JpaRepository<Post, Long> {
    // 기본 조회·저장 기능을 상속받아 사용할 수 있어요.
}

Optional<Post> post = postRepository.findById(42L);

트랜잭션: 여러 DB 작업을 하나의 약속으로

은행 송금은 보내는 쪽에서 돈을 빼고 받는 쪽에 넣는 두 작업이 모두 성공해야 해요. 중간에 실패하면 전체를 되돌려야 합니다. 이런 작업 단위를 트랜잭션 이라고 해요. Spring에서는 서비스 메서드에 @Transactional 을 적용해 트랜잭션 경계를 표현할 수 있습니다.

기초 주의 @Transactional 은 마법처럼 모든 오류를 되돌리는 표시가 아니에요. 프록시 호출 방식, 예외 종류, 데이터베이스 동작에 따라 결과가 달라질 수 있으므로 예외와 트랜잭션 규칙을 함께 배워야 합니다.

06

입력 검증과 오류 응답: 잘못된 요청을 안전하게 다루기

사용자가 보낸 값은 항상 확인해야 해요. 제목이 빈 문자열인지, 페이지 번호가 음수인지, 이메일 형식이 맞는지 검증하지 않으면 데이터가 잘못 저장되거나 예기치 않은 오류가 날 수 있습니다.

요청 데이터에 검증 규칙 선언하기 · 개념 예시
record CreateMemberRequest(
    @NotBlank String name,
    @Email String email
) {}

@PostMapping("/members")
MemberResponse create(@Valid @RequestBody CreateMemberRequest request) {
    return memberService.create(request);
}

검증 어노테이션을 쓰려면 관련 검증 의존성과 설정이 필요할 수 있어요. 검증 실패는 사용자에게 이해 가능한 오류 응답으로 바꾸어 전달해야 합니다.

오류는 구분해서 응답해요

상태 코드 예 뜻 상황 예
400 Bad Request 요청 형식이나 값이 잘못됨 필수 제목 누락
401 Unauthorized 인증 정보가 없거나 유효하지 않음 로그인 필요
403 Forbidden 인증은 됐지만 권한이 없음 다른 사용자 게시글 수정 시도
404 Not Found 요청한 자원을 찾을 수 없음 없는 게시글 ID
500 Internal Server Error 서버 내부에서 예상치 못한 실패 처리되지 않은 예외

오류 응답은 내부 경로나 SQL, 비밀 값이 드러나지 않게 하고, 문제를 해결하는 데 필요한 정보만 제공해야 합니다. 서버 로그에는 조사에 도움이 되는 요청 식별자를 남기되 민감한 값은 기록하지 않아요.

07

테스트와 설정: 바뀌어도 괜찮은지 확인하기

테스트는 코드가 기대한 규칙을 지키는지 자동으로 확인하는 프로그램이에요. 작은 함수는 입력과 결과를 비교하고, 여러 객체의 협력은 함께 실행해 확인할 수 있습니다.

테스트 종류 확인하는 범위 예
단위 테스트 작은 클래스나 규칙 하나 할인 금액 계산
슬라이스 테스트 웹 MVC 등 한 부분의 연결 Controller의 요청·응답
통합 테스트 여러 Bean과 구성 요소의 협력 요청부터 DB 저장까지

테스트는 구현 내부의 모양을 그대로 고정하기보다 사용자가 기대하는 동작을 확인하는 편이 유지 보수에 유리해요. 테스트 데이터와 실행 환경도 실제 운영 데이터와 분리해야 합니다.

설정은 코드와 환경에 맞게 분리하기

개발 환경과 운영 환경은 데이터베이스 주소, 로그 수준, 외부 서비스 키가 달라요. 설정 파일과 환경 변수를 이용해 환경에 맞게 값을 공급하고, 비밀 값은 코드 저장소에 기록하지 않습니다.

설정 파일 예시 · 실제 비밀번호를 여기에 적지 마세요
server:
  port: 8080

spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}

${DB_PASSWORD} 는 환경 변수 등 외부에서 제공하는 값을 읽도록 표현한 예예요. 운영에서는 권한 제한과 비밀 값 교체 절차도 고려해야 합니다.

08

인증과 인가: 누구인지 확인하고, 무엇을 할 수 있는지 판단하기

인증 은 사용자가 누구인지 확인하는 절차예요. 인가 는 확인된 사용자가 특정 기능이나 데이터에 접근할 권한이 있는지 판단하는 절차입니다. 로그인에 성공해도 모든 작업이 허용되는 것은 아니에요.

요청자격 정보 포함 → 인증누구인가? → 인가권한이 있나? → 기능 실행허용된 요청만

한 줄 설명 연습 “Controller는 요청을 받고, Service는 규칙을 처리하고, Repository는 데이터 접근을 맡는다.” 이렇게 자기 말로 설명해 보세요.

더 알아보기

트랜잭션 경계는 업무 작업 단위에 둬요

주문 저장과 재고 감소처럼 함께 성공하거나 취소되어야 하는 변경은 하나의 트랜잭션으로 묶습니다. Service 계층에서 여러 Repository 호출의 작업 경계를 표현하면 흐름을 이해하기 쉬워요.

서비스 메서드 예시
@Transactional
public Order createOrder(OrderRequest request) {
    Product product = productRepository.findById(request.productId())
        .orElseThrow(ProductNotFoundException::new);
    product.decreaseStock(request.quantity());
    return orderRepository.save(Order.from(product, request));
}

트랜잭션을 연 채 긴 외부 API를 기다리면 DB 연결과 잠금을 오래 점유할 수 있습니다. Spring 일부 기능은 프록시를 거치므로 같은 객체 내부 호출에는 적용되지 않을 수 있어요.

역할 나누기 Controller는 HTTP 입력과 응답, Service는 업무 흐름, Repository는 저장소 접근에 집중합니다.

심화

Spring 빈의 범위와 트랜잭션 경계

빈은 컨테이너가 만들고 의존성을 연결해요

ApplicationContext는 빈을 생성하고 의존 객체를 주입합니다. 생성자 주입은 필수 의존성을 생성 시점에 확인하게 해 테스트에도 편리합니다. 싱글턴 빈은 여러 요청이 공유하므로 요청별 상태를 필드에 저장하면 데이터가 섞일 수 있어요. 빈은 가능한 한 상태를 갖지 않게 설계하세요.

@Transactional은 프록시 경계를 통과해야 해요

Spring은 프록시로 트랜잭션을 처리하는 경우가 많습니다. 같은 객체 내부에서 메서드를 직접 호출하면 프록시를 통과하지 않아 애너테이션이 적용되지 않을 수 있습니다. 서비스 작업 경계에 트랜잭션을 두고 외부 네트워크 호출을 오래 포함하지 않도록 합니다.

  • 컨트롤러는 HTTP 입출력, 서비스는 작업 흐름, 저장소는 데이터 접근을 맡습니다.
  • 요청 DTO의 형식 검증과 도메인 규칙 검증을 구분합니다.
  • 비밀번호와 키는 외부 설정으로 주입하고 저장소에 커밋하지 않습니다.

초보 Spring 용어사전

Spring 코드를 읽을 때 자주 만나는 말을 모았습니다.

용어 한 줄 뜻
프레임워크 애플리케이션의 기본 구조와 반복 기능을 제공하는 틀.
Spring Boot Spring 애플리케이션 설정과 실행을 쉽게 시작하도록 돕는 도구.
IoC 객체 생성·연결의 제어를 프레임워크에 맡기는 설계 원칙.
DI 객체가 필요한 협력 객체를 외부에서 전달받는 방식.
Bean Spring 컨테이너가 생성하고 관리하는 객체.
Controller 웹 요청을 받고 HTTP 응답으로 연결하는 역할.
Service 애플리케이션의 업무 규칙과 작업 흐름을 맡는 역할.
Repository 데이터의 저장과 조회를 맡는 역할.
DTO 계층이나 API 사이에서 데이터를 전달하는 객체.
Entity 애플리케이션에서 지속적으로 관리할 도메인 데이터 객체.
JPA Java 객체와 관계형 데이터베이스를 다루는 표준 명세.
트랜잭션 함께 성공하거나 실패하도록 묶은 데이터 작업 단위.
인증 사용자가 누구인지 확인하는 절차.
인가 사용자가 특정 작업을 해도 되는지 권한을 확인하는 절차.
