웹 보안 기초

🛡️

사용자가 보낸 데이터는 신뢰하지 말고 검증하세요.
브라우저에서 숨긴 버튼도 직접 HTTP 요청을 보내면 우회할 수 있어요. 중요한 검증과 권한 확인은 서버에서 수행해야 합니다.

01

보안의 목표: 기밀성·무결성·가용성

보안은 비밀번호를 감추는 것만이 아니에요. 승인되지 않은 사람이 읽지 못하게 하고, 데이터가 몰래 바뀌지 않게 하며, 필요할 때 서비스를 쓸 수 있게 지킵니다.

목표 쉬운 뜻 예시
기밀성 허가된 사람만 정보 열람 개인 정보를 권한 없는 사용자에게 감춤
무결성 정보가 허가 없이 바뀌지 않음 주문 금액을 임의로 조작 못 하게 검증
가용성 필요한 시점에 시스템을 사용 장애와 과부하에 대비한 복구 계획

세 목표 사이에는 균형이 필요해요. 보호를 강화하면서도 정상 사용자가 안전하게 쓸 수 있는 흐름을 설계해야 합니다.

02

인증과 인가: 누구인지, 무엇을 허용할지

인증 은 신원을 확인하는 것, 인가 는 그 신원에 어떤 동작을 허용할지 확인하는 것입니다. 서비스는 요청받은 객체가 실제 그 사용자의 것인지 매번 서버에서 검사해야 해요.

인증로그인 정보 확인 → 인가역할·자원 권한 확인 → 기능 실행허용된 동작

비밀번호 저장과 로그인 세션

비밀번호는 평문으로 저장하지 않아요. 검증된 비밀번호 해시 함수로 단방향 변환하고, 사용자마다 고유한 salt와 적절한 비용 설정을 사용해야 합니다. 일반적인 빠른 해시(SHA-256 등)만 적용하는 것은 비밀번호 저장용 대안이 아닙니다.

방식 서버가 기억하는 것 주의할 점
세션 서버 저장 상태와 브라우저 쿠키 식별자 쿠키 보호·만료·CSRF 고려
토큰 서명된 토큰 검증 정보 유출·만료·폐기와 저장 위치 고려
비밀번호 안전한 해시 결과 원문 또는 복호화 가능한 형태 저장 금지
03

입력 검증: 공격자가 보낸 값도 평범한 입력처럼 보여요

입력은 길이·형식·범위·업무 규칙을 검증하세요. 그러나 입력값을 검사하는 것만으로 모든 공격을 막을 수 있는 것은 아니에요. 사용하는 맥락에 맞는 안전한 API와 출력 처리가 함께 필요합니다.

SQL Injection

사용자 입력을 SQL 문자열에 그대로 이어 붙이면 입력이 SQL 명령의 일부로 해석될 수 있어요. Prepared Statement나 ORM의 파라미터 바인딩을 사용해 데이터와 명령을 분리합니다.

문자열 결합 대신 파라미터 바인딩
// 위험한 방식: 입력이 쿼리 문법에 끼어들 수 있음
"SELECT * FROM users WHERE name = '" + name + "'"

// 안전한 방향: 쿼리와 값 분리
SELECT * FROM users WHERE name = ?

XSS 는 공격자가 넣은 스크립트가 다른 사용자의 브라우저에서 실행되는 문제예요. 출력할 때 HTML 맥락에 맞게 인코딩하고, 신뢰하지 않는 내용을 위험한 HTML로 해석하지 않도록 해야 합니다.

CSRF와 사이트 간 요청

CSRF는 사용자가 로그인된 브라우저를 속여 원치 않는 상태 변경 요청을 보내게 하는 공격이에요. 쿠키 기반 인증에서는 CSRF 토큰, SameSite 쿠키 설정, 요청 출처 검증 등 적절한 방어를 구성합니다. GET 요청으로 상태를 바꾸지 않는 것도 기본 원칙이에요.

04

통신과 비밀 값 보호

HTTPS는 HTTP 통신을 TLS로 보호해 전송 중 내용을 암호화하고, 연결한 서버가 인증서에 맞는 서버인지 확인하도록 도와요. 그래도 서버 안에 저장된 데이터를 자동으로 모두 암호화하거나 애플리케이션 버그를 막아 주는 것은 아닙니다.

비밀 값은 코드 밖에서 관리

데이터베이스 비밀번호, API 키, 서명 키를 코드·Git 기록·로그·스크린샷에 남기지 마세요. 환경 변수나 비밀 관리 도구에서 제공하고 접근 권한을 제한합니다. 노출이 의심되면 기록에서 지우기만 하지 말고 키를 폐기하고 교체해야 합니다.

위험 예방 습관
네트워크 도청 HTTPS 사용, 인증서 검증
비밀 값 유출 저장소 밖에서 관리, 최소 접근
로그에 개인정보 노출 필요한 값만 기록하고 민감 정보 마스킹
오래된 키 재사용 교체·폐기 절차와 접근 감사
05

최소 권한과 외부 라이브러리

계정·프로세스·서비스에는 맡은 일에 필요한 권한만 주세요. 데이터베이스 앱 계정에 모든 테이블 삭제 권한까지 줄 이유가 없다면, 권한을 줄여 사고의 피해 범위를 제한할 수 있습니다.

의존 라이브러리도 공급망의 일부

외부 패키지는 개발 시간을 줄여 주지만 알려진 취약점, 잘못된 업데이트, 출처 위험을 가져올 수 있어요. 필요한 라이브러리만 쓰고 버전을 관리하며, 취약점 알림과 업데이트를 꾸준히 확인합니다.

영역 기본 점검
권한 사용자·서버·DB 계정의 불필요한 권한 제거
의존성 불필요한 패키지 제거, 보안 업데이트 검토
오류 응답 스택 추적·SQL·내부 경로 노출 방지
파일 업로드 크기·종류·저장 위치와 실행 가능성 점검
관리 기능 인증·인가와 접근 기록을 적용
06

보안은 반복 점검과 대응 계획

위협 모델링은 무엇을 보호할지, 누가 공격할 수 있는지, 데이터가 어디로 흐르는지, 어떤 약점이 있는지 미리 생각하는 과정이에요. 새 기능마다 작은 위협 검토를 하면 나중의 큰 수정 비용을 줄일 수 있습니다.

  1. 보호할 데이터와 중요한 기능을 적습니다.
  2. 사용자·관리자·외부 시스템 등 행위자를 확인합니다.
  3. 데이터가 이동하고 저장되는 경로를 그립니다.
  4. 인증·권한·입력·비밀 값·로그를 점검합니다.
  5. 사고가 나면 키를 교체하고 서비스를 복구할 순서를 정합니다.

보안은 한 번 체크하고 끝나는 작업이 아니에요. 새 취약점과 서비스 변경에 따라 패치를 적용하고, 백업 복구와 사고 대응을 연습해야 합니다.

공격 종류에 맞는 방어를 적용해요

SQL 문자열에 입력값을 이어 붙이면 입력이 SQL 명령으로 해석될 수 있습니다. 쿼리와 값을 분리하는 매개변수 바인딩을 사용하세요.

SELECT id, name
FROM users
WHERE email = ?

각 공격은 발생 위치와 방어 방법이 다릅니다. 입력 검증 하나에 기대지 말고 각 경계에 맞는 보호를 겹쳐 적용하세요.

위협을 먼저 찾고 방어를 여러 겹으로 쌓기

위협 모델은 자산과 공격 경로를 정리해요

사용자 정보, 결제 데이터, 관리자 기능처럼 보호할 대상을 정하고 누가 어떤 경로로 악용할 수 있는지 생각합니다. 입력 검증과 권한 검사 누락, 비밀 유출, 과부하를 위험으로 적고 가능성과 영향도에 따라 우선순위를 정하세요. 각 위험에 예방·탐지·복구 방법을 연결하면 대응이 구체적입니다.

비밀번호와 비밀 값은 노출돼도 피해를 제한해요

비밀번호는 복호화 가능한 형태나 빠른 일반 해시로 저장하지 말고 salt를 사용하는 전용 비밀번호 해시 함수를 사용합니다. API 키는 코드에 넣지 않고 제한된 비밀 저장소에서 관리하며 노출되면 폐기하고 교체합니다. 입력은 서버에서 다시 검증하고 출력 문맥에 맞게 인코딩해 스크립트 삽입을 막습니다.

  • 최소 권한과 다중 인증으로 계정 탈취의 영향을 줄입니다.
  • 로그에서 인증 정보와 개인 데이터를 제외합니다.
  • 패치와 복구 훈련을 정기적으로 수행합니다.
